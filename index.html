01 · 工具栈演变

从终端里编排 CLI agent，到在 GUI 和云端搭一个能自己跑的厨房。

Meta 时期的 Claude Code → Cursor → Grok Bot

  1. 2025-04

    React Compiler MCP 实验。想让 agent 拿到人用的信号（编译器诊断、lint）；后来认为 MCP 这个载体选错了。（#20）

  2. 2025 年末～2026-03

    Meta + Claude Code。"At Meta, Claude Code was explosively taking off. I even paid for a personal $200 a month plan for my side projects."

    自己写技能把 cc 改造成想要的样子，还在上面做编排器（noodle）。分工上 Claude 当 manager、Codex 当 coder，Codex 做对抗评审（#4、#6）。用 deepcoding 插件先装好上下文再写代码（#2）。出处 #13、#8。

  3. 2026 年 1～2 月

    倦怠期的副业。离开 Meta 前后休了一个月，开始做副业，发现自己“花好几个小时微操一个 agent”，技能效果也没法衡量（"flying blind"）。这段经历成了 pstack 的雏形。（#64）

  4. 2026-03 底

    加入 Cursor。面试那两天第一次用 Cursor。三点印象：随时切换、混用模型（Opus 写前端、Codex 写系统）；压缩上下文极快；GUI 比 TUI 能做更多。

    入职第二天就被拉去修 Agents Window（内部代号 glass）的性能 → 写出 /control-glass → 加 worktree 隔离 → Cursor Automations（Benny）→ 2026-05-25 开源 pstack。（#13、#20）

    模型从 Opus/Codex 转向 Grok 4.5 fast（#24）、Grok 4.6（#32），后来是 Grok 4.7 xhigh（#69）。pstack README 默认配置：写代码交给 grok，最难的改动、文字和判断交给 Opus 5.5。

  6. 2026-07 起，08-11 发布

03 · 验证

验证技能是关键基础设施：一个 CLI，加一张 Feature Map。

"the most critical skill to have in your toolbox is a high quality verification skill… I think of it more like critical infrastructure" #52

"Done well, you will 100-1000x your whole team's output"；她甚至建议给它排 oncall（#52）。

定义：agent 能像真实用户一样运行和操作产品，还能 debug、抓 trace、抓 heap snapshot，从而 "close the loop"。它保证的是正确，不保证代码好（#30、#77）。

起源 /control-glass：通过 Chrome DevTools Protocol 启动 dev build，能点击、输入、读无障碍树、截图、录屏、限速 CPU/网络、抓 CPU profile 和 heap snapshot（#20）。

两个组成部分 #59

1. CLI

别让每个 agent 都 “rebuild the world each time”。

把确定性的部分写成脚本，判断留给 agent："I try to extract out the deterministic parts and turn that into code and just leave only the parts that actually require judgment to the agent."（#64）

  • 可组合（参考 Ousterhout 的 deep modules）
  • 危险命令带 --dry-run
  • 用子命令逐步暴露功能
  • 错误信息告诉 agent 该怎么做
  • --help 写全
  • 输出 JSON（agent 友好 CLI 的特征，#52）

2. Feature Map

"a form of materialized memory"

所有功能怎么从用户视角找到、怎么用 CLI 操作、有哪些坑；也是代码库这一“终极记忆”的压缩版（#52）。

要每天跑 /maintain-verification-skill，因为它过期很快（#25）。

证据比解释可靠。

"'I fixed it' isn't good enough. Show me the failing test and the passing test. Show me the before and after video." #20

她现在主要看的就是 agent 在自己 VM 里录的视频和截图（#70 附近的回复）。

每一步都能叫停："every stage can stop the line"。triage 可以判定“这不是 bug”，repro 可以复现失败，fixer 可以判定“改动风险太高”（#20）。

往上走是形式化方法：TLA+、Lean、Bend（#64、#77），但她自己没走这条路（T8）。

04 · 约束和 lint：代码库就是记忆

每次纠正 agent，都想想怎么让这个问题彻底消失。

架构 > lint/CI > 技能/规则 > 人工 review

纠错层级：
  1. "categorically eliminate the problem through better architecture or choice of data structures"
  2. "turn it into a lint rule or test so CI catches it"
  3. "turn it into a skill or rule"
  4. "have humans review the code to catch it (ngmi)"
#34

为什么：agent 会照抄已有的模式，坏模式会 "spread kind of like a virus"（#59）。

"the best rules are in your code. invest accordingly." #22

"refactoring your codebase and choosing a tech stack with strong type systems/compiler diagnostics has far greater impact than AGENTS.md and tweaking your skills."（#22）

Dune

"the shortest path is the best path"

Grok Bot 的自研 Electron 客户端框架，没有开源。agent 爱走捷径，那就让捷径就是正确的路（#30）。

  • 起因：早期 Grok Bot 有 "eight god files… at least 10,000 lines"（#64）；她做了 600 多个重构 PR（#30）。
  • 规则：功能各占一个目录；main 和 renderer 进程之间的 import 依赖图由 CI 检查；禁用 useEffect；禁用代码注释，理由："agents were just using the comments around the code as justification for why it wasn't going to solve the actual problem"（#30、#59）。
  • 效果：PM、设计师、GTM 也能直接提 PR；"it's actually very annoying to write code in… but agents absorb all of that annoyance"（#30）。

园丁

"every weed you pull becomes a rule, so it can't grow back."

（#40）她的做法：一个 agent 一直扫 React 的禁用模式，但不直接修，而是追加到一个文档里；她每隔几天看一次，找出共同根因再派活（#64）。

/correct 与 TTR

/correct（0.15.9，#65）从历史中挖出 agent 反复犯的错误类型，按“架构 → 类型/lint/CI → 测试 → 文档”的顺序修掉。她用盆景比喻：提交像疯长的盆景，要用约束有意识地修剪。

衡量指标思路 TTR："time to (fully automated, hands off) rewrite"（#71）。

对 slop 的立场：

"you are a software engineer… and now you can't do anything about it?" #77
"agents are like a mirror. If you guide it and constrain it well, it can produce code you consider good." nitter 回复

05 · 像管团队一样管 agent

agent 是永远失忆、但很好教的新员工。

她在 Netflix 当过约两年的 EM，在 Meta 当过 React 的 EM，后来又回到 IC。

"Agents are like new hires in a constant state of amnesia and idiocy. They don't remember what you tell them, and they never really learn anything new. But we can equip them with rules, skills, tools, and long term memory which can approximate that. They're capable yet stupid, and very teachable." #13

管理杠杆：

"High Output Management calls this idea 'managerial leverage'. Applied to agents, it's the idea that humans can do the work once by authoring reusable skills and tools, and increase the output of your whole agent team." #20

Netflix 的 "context not control"：靠给上下文，而不是靠微操；教 agent 自己去取上下文（#64）。

信任和放手："when you have little trust, you must micromanage each and every agent. When you can let go, you can delegate more. this is exactly like managing people!"（#10）

米其林厨房，不是软件工厂

"I'm not a fan of the term software factory. I like the analogy of a Michelin kitchen better"

（#59）家庭厨师 → 一家人挤在厨房 → 主厨（"the CEO of the kitchen"）→ 像 Gordon Ramsay 一样开连锁店，每个大项目就是一家店（#64）。

评审改为抽样

"you cannot be tasting every single dish… So it becomes more about sampling"

像质检员一样；只有多个 agent 犯同样的错时才去改环境（#64）。

其他值得一提的习惯

  • 先让 agent 用自己的话复述你的目标（#62、#55）。
  • 写作坚持自己写："i still strongly believe that writing is thinking… words become the interface between you and the genie"（#78）。
  • 领域知识更重要了："the bottleneck is no longer the agent… it becomes your ability to express your intent"（#64）。
  • 盯着 agent 的思考块找失败模式："When I'm in the loop, I pay close attention to the chat, especially thinking blocks."；"If a script can do it deterministically, use the script."（#20）

06 · pstack 和 /poteto-mode

把观察到的失败模式，全部变成技能。

名字在调侃 YC CEO Gary Tan 的 gstack（两人同姓，没有亲属关系）（#30）

"pstack teaches agents to be more rigorous using multiple models. I've taken all the failure modes I've observed and turned them into skills." #13

定位是 "my personal set of skills and engineering principles"；"The goal is not maximal LOC, but the opposite: maximum impact with the least amount of code."（#13）

结构

README / Barnaby 统计 0.15.9：

  • 一个路由器 /poteto-mode
  • 23 个 playbook、二十几个技能、24 条原则技能
  • 2 个子 agent：poteto-agent、Comment Sicko
  • Benny 自动化包（默认不启用）

用法

任务开头加上 /poteto-mode，例如：

"/poteto-mode i'm going to bed. land the stack even if ci flakes. i want everything merged by morning."

按 Opt+Enter 可以设成 Custom Mode 常驻；配合 Cursor 的 /loop 可以连续工作好几个小时（README）。

常用技能

/how、/why（并行查 git、工单、文档、Slack、Datadog、Sentry、数仓）、/recall（从历史对话恢复上下文）、/teach、/architect（多模型族给出竞争方案，再由另一个模型当裁判）、/arena、/swarm、/interrogate（多模型对抗评审）、/tdd、/unslop、/reflect、/figure-it-out、/show-me-your-work（只追加的决策日志 TSV）、/automate-me（从你的对话记录生成你自己的 -mode）、/correct、/benchmark-checklist、/in-your-own-words、/ketchup、/poteto-help、/make-bot-ui。

规划观："personally, i don't believe in planning. the best spec is code."（README）

"Prototyping is planning, but with code." "abstract plans only give you the illusion of progress." #55

技能要经过 eval：eval playbook 是盲测的，子 agent 的目录名故意起得不让它察觉自己在被评估，因为 "agents can actually tell and when they do they change their behavior"；可以用 /loop 爬分到 10/10（#30）。"for my own skills in pstack I also do run evals on them"（nitter 回复 Geoffrey Huntley）。

技能会越来越短："skills from last year were really more about… exact script commands… with the latest models you can just delete those parts and just really focus on the workflow"（#64）。

各自打造自己的刀："every chef has their own set of knives, you should too or just use pstack heheh"（#19）；"fork it. improve it. make it yours."（README）

软件工厂 / 米其林厨房和 Benny

早期说法："true agent parallelism, like in a dark factory for software, might be possible"（#13）。Benny 三段式（#13、#20）：

01

Slack 报告进来

Triage 分诊

读截图和视频、查重、查 git 历史、查 Notion 判断“是 bug 还是设计如此”，必要时追问报告人。

02

云端 Cursor

Repro 复现

用 computer use 照着报告人的路径走，必须连续两次复现到坏状态，并录屏。之后人有机会否决。

03

draft PR

Fix 修复

能写测试就先写测试，做最小改动，对比前后，开 draft PR，附视频。

迁移的经验（StyleX，#20）：一次性的 40 万行巨型 PR，dogfood 时仍然暴露出 z-index 和优先级问题。于是改成每天迁移一个叶子组件，在三套主题和各种交互状态下比对 computed style。"catch defects at the lowest value stage"。

"our job is not merely to produce software any longer… but the machine that writes the software. this idea of a software factory, or a Michelin kitchen as i like to call it" 她后来对“工厂”的定义，#72

现在的 PR 主要来源：重构、性能、bug 修复；"most of the volume of PRs i land are refactoring"（#70、#73、nitter 回复）。PR 尽量原子化，不设硬上限，因为 "the git history is a very rich source of context"（#30）。

07 · 两个循环

Grok Bot 是外环，Cursor Projects 是内环。

"cursor projects are my inner loop and grok bot is my outer loop"（#64）

外环 · Grok Bot

盯 Slack、X、邮件、Linear，发现相关问题就发给对应的 Cursor Project。

"I have the equivalent of like more than 10 chiefs of staff…"

"…one that's working on performance… one that's working on fixing bugs that users report… one that's exploring rewriting it in a different language just for fun"（#64）

内环 · Cursor Projects

协调者 agent "doesn't do the work itself. It delegates and orchestrates"。

它会把 30 个相关报告合在一起找共同根因，而不是开 30 个互不相干的修复（#64）。

每天跑的 loop（#68）：

  1. "watch this slack channel for feedback…"
  2. "create a ticket for this in Linear"
  3. "create a Cursor cloud agent to triage and reproduce the issue on its own computer, using pstack"
  4. "if the issue clearly reproduces, put up a fix and fuzz the pull request with a small swarm of agents"
  5. "if the fuzz has no issues, ping me on Slack, and rebase and auto-merge the PR after 1 hour unless i request changes"

发版和 QA（#69）：sandcastle（发版经理 bot）在 Slack 里私信每位贡献者确认 PR → 构建 → 10 多个 Grok 4.7 xhigh agent 组成 fuzz 蜂群（有定向测试，也有“混沌猴子”）→ @工程师 bot poteto 开一个 Cursor Project 修高优先级问题 → 必要时 cherry-pick 发补丁版本。

X 上的反馈：回复她 X 提及的 bot 把问题转到 Slack，另一个 bot 用 pstack 复现并修复（nitter 回复 2108253488451100877）。

入门方式：Dr Eggbot（生成高质量 bot 的 bot）→ 让它建一个工程师 bot → 跑 /create-verification-skill → 设每日 routine 跑 /maintain-verification-skill（#52、#74）。

在 Grok Bot 里的提示方式（bot 只当协调者，保持自己的上下文干净，#52）：

"spawn a cloud agent to use /poteto-mode to build … use /control-app to verify your changes and show me a video and screenshots as proof"

不需要什么“公司大脑”："Some people call this like a company brain… I personally don't think you need anything that sophisticated here because agents are really good at using tools."（#59）

08 · token 成本

前期把 token 花在环境上，长期反而省。

日期均为 2026 年

  1. 05-25

    "using multiple agents, especially frontier ones, use a lot of expensive tokens. i'm hopeful that future versions Composer can change that."（#14）

  2. 06-10

    "i think of it as moving the tokens you would've otherwise spent on reworking things earlier. measure twice, cut once"（#18）

  3. 07-29

    便宜又快的模型（Grok 4.5 fast）让每个 PR 都能跑“验证蜂群”（#24）

  4. 08-12

    "obviously, you know, I work at a AI lab where we have unlimited tokens… I think to me it's a question of ROI"

    前期重构很费 token，但能让“最笨的 agent”也写出好代码，不用多招人（#30）

  5. 08-23

    routine 别设太频繁，周期任务交给新开的 bot（#41）

  6. 08-25

    "an efficient model like Grok 4.6 non fast is key"（#43）

  7. 08-27

    "i probably average about 15b tokens / day"（自述，#45）

  8. 09-12

    预算有限就用 /setup-pstack 选便宜模型；pstack 少出 bug 也是省钱（#57、#58）

  9. 10-02

    full autopilot 给每个 PR 配约 10 个 verifier，"quite token intensive. You can tune this… instead of like 10 verifier agents you might do like one"（#64）

  10. 10-04

    "if you spend the tokens upfront to improve your agents' environment so they fall into a pit of success, you'll spend less tokens in the long run"（#66）

  11. 10-07

    /setup-pstack 可以设预算；验证本身就是 token 效率（nitter 回复 2107949669695582437、2107922229711585334）

  12. 10-08

    "i think about this in terms of cost per intelligence… what looks exorbitant today will likely be affordable in 6 moths to a year"（#72）

  13. 10-11

    pstack 瘦身 10%（"less tokens"）（#76）

  14. 第三方

    Rob Shocks 实测：用 pstack 约 1 小时，不用约 30 分钟，更费 token，但抓到 3 处 agent 幻觉（T4）

09 · 需要注意 / 未核实

流传最广的几句话，她本人没说过。

⚠️ 病毒式营销帖

X 上有不少帖子（如 @0xMovez、@sheemamoto、@proAlishke）声称她说过 “Chief of Staff + 3 managers + 16 workers”、“只有 1% 的人用对了 GrokBot”、“$850,000 offer”等，还有所谓 “GrokBot Agent Team Harness” 文件。

核对了两份完整逐字稿（Maven 工作坊、Matt Pocock 访谈），都没有这些原话。她本人只说过 "more than 10 chiefs of staff, each working on a different area"（Pocock 访谈），以及“可以做一个 mother bot 来生成你的 chief of staff”（#50）。以上说法应视为第三方二次加工。

关于“产量”数字（都是自述，未核实）

  • 2026-07 约 1,000 个 PR（#37、#30）。
  • 2026-08 约 2,000（Pt.1、演讲口播）；X 标题写 2,500；Pt.2 提到 8 月底是 2,462（T4 转述）。T8 也指出了标题和口播的差别。

  • 7/20 以来 2174 个 PR，中位数 +177/−29，平均 +746/−394（#38）。
  • 她自己强调：2,500 个 PR 不等于 2,500 个功能，大量是“园丁”式工作（#64）；volume 只有建立在信任上才有意义（#72）。
